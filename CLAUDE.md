## What this is

A native Android app (Kotlin + Jetpack Compose) that teaches DSA, C, Linux kernel, and networking concepts via frame-based step animations. It's a reference implementation ported from the web app (dsa_website) architecture: **one Frame per animation step, one Player engine owns playback, multiple Scene/Renderer pairs per domain**.

The app is fully offline, with all content bundled as JSON asset files and frames generated by Kotlin algorithm runners.

### Architecture

**Core frame-based playback** (reused from web app):
- `Frame` data class: narration, phase, codeLine, stats, and a domain-specific `Scene` object
- `PlayerViewModel`: owns `StateFlow<PlayerState>` (frames list, current index, play/pause/speed)
- Player engine: play, pause, step, scrub, reset, speed control — no domain-specific logic
- Renderers: `@Composable` functions that draw a `Scene` on Compose Canvas (BarsRenderer, TreeRenderer, etc.)

Example flow:
```kotlin
// 1. Run algorithm → generate frames
val frames = BubbleSortRunner.run(array)

// 2. Load into player
playerVM.loadFrames(frames)

// 3. Player handles UI (buttons, scrubber, animation timing)
// 4. Frame's scene → Renderer → Canvas
```

**Project structure**:
```
app/
  src/main/java/com/interviewpreplab/
    core/
      model/Frame.kt, Scene types (BarsScene, TreeScene, etc.)
      player/PlayerViewModel.kt, PlayerState
      ui/BarsRenderer.kt, TreeRenderer.kt, ... (Canvas-based renderers, one per scene type)
    features/
      sorts/BubbleSortRunner.kt, ... (algorithm runners; each produces Frame list)
      searches/
      data_structures/
      kernel/ (new domain)
      networking/ (new domain, L2/L3/L4)
    ui/theme/Theme.kt, Color.kt, Type.kt
    MainActivity.kt (entry point: loads demo topic, ties UI together)
  src/main/res/
    values/strings.xml, themes.xml
    xml/backup_rules.xml, data_extraction_rules.xml
  build.gradle.kts (Compose, Material3, Room, DataStore, Hilt)
```

## Adding a new topic

1. **Create a runner** (`features/<domain>/<TopicRunner>.kt`):
   - `object BubbleSortRunner { fun run(array: List<Int>): List<Frame> }`
   - Generate frame list: narration, phase, stats, and a Scene object
   - Unit test: verify frame count, final array state, stats accumulation

2. **Create renderer** if new scene type (e.g., `TreeScene`):
   - `@Composable fun TreeRenderer(scene: TreeScene, ...)` in `core/ui/`
   - Use Canvas + Compose state for smooth animations
   - Reference existing renderers (BarsRenderer) for animation patterns

3. **Wire into UI**:
   - Add to topic list or home screen
   - Pass runner output to `PlayerViewModel.loadFrames()`
   - Compose UI calls renderer with current frame's scene

4. **Test**:
   ```bash
   ./gradlew test  # Test runner output
   ./gradlew connectedAndroidTest  # Test UI/renderer on device
   ```

## Ports from web app

**DO copy these patterns from the existing web code** (`dsa_website/`):
- Narration text and phrasing (keep second-person voice: "Out of order, so swap them.")
- Role naming for visual highlighting ("compare", "sorted", "landed", "found", "dim")
- Algorithm logic from `runX()` functions; port JS to Kotlin 1:1
- Cell role animations from HTML examples (use Compose `animate*AsState` to morph between frame states)

**DONT**:
- Use old `DSRender`/`ds-engine.js` JS patterns directly; translate to Kotlin
- Copy HTML/CSS; build UI with Compose + Material3

## Testing approach

- **Unit tests** (`src/test/`): each `*Runner` class → verify frame list structure (length, final state)
- **Frame-contract validator**: assert `frame.array.length == frame.roles.length`, `codeLine` in range
- **Manual on device**: run algorithm, scrub back/forward, rotate screen (state survives), tap play/pause

## Performance notes

- Target 60fps playback; avoid allocations in draw lambda
- Canvas recompositions only on frame change (use `remember(frame)` guard)
- Profile with Android Profiler: CPU → Show Frames Jank
- Tablet layout: use `WindowSizeClass` to adapt (single-pane on phone, list-detail on tablet)

## Key decisions

- **Frame as data, not code**: algorithms pre-generate frames; UI just displays them (no real-time computation)
- **Offline-first**: all content in assets/, no backend
- **Reusable player**: one ViewModel drives all topics; all domains (DSA, kernel, networking) use the same playback controls
- **Canvas + Compose for rendering**: smoother animations than full View redraw; precise control over timing
